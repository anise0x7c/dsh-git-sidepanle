# Git source control

A Code OSS-style source-control surface for the right Sidebar. It reads the Git repository that contains the current Session's working directory and lets you review and act on it without leaving the Web GUI.

The panel is drawn with the host's own theme tokens, type scale, and component conventions, so it follows light and dark themes and matches the Sidebar's headers, dividers, controls, and menus. Every list row — changed files, commit rows, commit-details folders and the files under an expanded commit — uses one compact 22-pixel row style, so the change lists and the graph share the same rhythm.

The panel body has two top-level sections: **Workspace**, which holds the working-tree change groups, and **Commit graph**, which holds the history.

## Open it

Open the right Sidebar (the expand control at the conversation header's right corner), then pick **Source control** on the guide page. The same page opens with the sidebar shortcut — `Ctrl+Shift+G` (`Cmd+Shift+G` on macOS) — in the desktop app and in the Windows and macOS Web interface. Linux Web browsers reserve that combination, so no default shortcut is registered there; assign one in DSH's keyboard settings.

The Git tab and its diff tabs live in the right Sidebar's normal docking surface, so they can be split, floating, or restored with the Sidebar's saved layout.

When the Session's working directory is not inside a Git repository, the panel names that directory and offers only a refresh. If the Host cannot run Git, it explains how to make Git available and offers retry.

## What it shows

- **Branch header**: the checked-out branch, detached or unborn state, upstream tracking, and ahead/behind counts. Pick the header to switch to another local or remote-tracking branch. The remote actions live in the commit graph's section header. While the panel loads on open, refreshes, loads earlier commits or runs a Git operation, a thin indeterminate bar sweeps along the toolbar's bottom edge. It shows immediately, stays for at least half a second even if the work finishes sooner, and keeps sweeping without a gap when more work starts during that hold; it takes no layout height or pointer input, and holds still when reduced motion is preferred.
- **Commit box**: a multi-line message with `Ctrl+Enter` (`Cmd+Enter` on macOS) to commit. The box is one line high until the message wraps, grows with it, and stops at ten lines, where the message scrolls instead of pushing the change list down. The commit action fills the box width as a primary button with a check icon, and the chevron at its trailing edge opens a menu with **Commit**, **Commit (Amend)**, a separator, **Commit and Push**, and **Commit and Sync**; Escape, a click outside, or the start of an action closes the menu. Both halves form one control: an empty message or a running action disables and dims them together, and the menu cannot open then. Every action commits staged changes only. When nothing is staged, Commit, Commit and Push and Commit and Sync offer to stage every change first, while Commit (Amend) stages nothing. Commit (Amend) replaces HEAD with the typed message and the staged changes and is refused when the branch has no commit yet. Commit and Push commits and then pushes; Commit and Sync commits, pulls by merging, then pushes only when the pull succeeded; both are unavailable when the branch has no upstream, and a failed remote step keeps the commit that was created. A failed commit keeps the message and the staged files, and the main button's tooltip still explains which changes a commit picks up. When the working tree has no changes, the branch tracks an upstream, and it is ahead of that upstream, the box's primary button becomes **Sync N Changes**, naming how many local commits are waiting to leave: it needs no message, it replaces the commit modes and their menu, and pressing it runs Sync, pulling the upstream by merge and then pushing. As soon as the workspace has a change to commit the button returns to Commit, and a branch without an upstream never shows it.
- **Workspace**: the working tree as a collapsible top-level section. Inside it, Code OSS's three change groups — **Merge changes**, **Staged changes** and **Changes** — are nested collapsible groups in that order, indented one level along with their rows and each keeping its own file count, its bulk stage, unstage and discard controls, and its context menu. Each group is a single-layer, path-sorted list with no folder rows. Every row shows the file's own file-type icon (the glyph and color the Web application's explorer uses, with the plugin's plain document icon as the fallback), the file name, its dimmed parent directory, and the status letter (`M` modified, `A` added, `D` deleted, `R` renamed, `U` untracked, `!` conflicted) at the row's end in that status's color, as the files under an expanded commit do; the full path is in the row tooltip. Hovering a row keeps the whole row highlighted, and the stage, unstage, or discard buttons it reveals add their own highlight while the pointer rests on one of them. Every row is 22 pixels high and shares the commit graph's row style. Collapsing Workspace hides all of its groups, while collapsing one group hides only that group's rows. When the working tree is clean, the Workspace section says so in text, without an icon, instead of listing empty groups.
- **Resizable panes**: the Workspace section scrolls in its own pane above the Commit graph, so a long change list does not bury history. Drag the divider between them to change the split; with the divider focused, `ArrowUp`/`ArrowDown` move it by 5%, `PageUp`/`PageDown` by 10%, and `Home`/`End` jump to the limits. Each pane keeps a usable minimum height and its own scroll position. Collapsing the Workspace section folds its pane to the Workspace header; when that section stays open but every nested group is collapsed, the pane folds to the Workspace header plus the group headers. Collapsing the Commit graph folds it to its header at the bottom edge of the panel. In every case the other pane takes the room, the pane folds with a short animation, and its rows stay visible while the shrinking pane clips them. The divider stays visible between the panes while a pane is folded but is inert in that state: it keeps its hairline, shows no hover highlight, accepts no drag, takes no keyboard focus and changes no ratio. Expanding the Workspace section, any nested group, or the Commit graph restores the ratio in effect before the fold and makes the divider operable again. Reduced motion takes the new height at once. The ratio survives opening a commit's details and returning, but resets when the tab is closed and reopened.
- **Pinned headers**: while the Workspace lists more rows than its pane, the Workspace header stays at the pane's top edge and the header of the group in view pins directly below it as you scroll, painted on the panel surface so the rows pass beneath them and nothing shows above either header or between them. Both headers already sit in those positions before the pane is scrolled, so beginning to scroll moves only the rows. The next group's header takes the pinned place as the previous group leaves, so only one group header is pinned at a time. The commit graph header pins at the top edge of its own pane the same way. Hovering a header highlights it as a whole, and the action controls inside it — a group's bulk actions or the commit graph's remote controls — add their own highlight while the pointer rests on them; the collapse toggle spans most of the header, so it keeps only the header highlight.
- **Commit graph**: a Code OSS-style Source Control Graph for recent commits across local branches, tags, and remote-tracking branches, listed in topological order as Code OSS's "All" filter lists them. Lines follow Code OSS's swimlane rules: a commit sits on the leftmost line heading for it and its first parent continues there; further lines heading for the same commit curve into its node on that row; each extra merge parent opens a new line at the right end; and lines to the right of an ended line shift left. Rows are 22 pixels high with an 11-pixel lane pitch, thin lines, quarter-turn joins and merges, and short S-turns for shifts; a lane stays unbroken where two rows meet, at any zoom. Nodes use Code OSS's shapes — a dot, a ring around a dot for merges, and a hollow ring for the checked-out commit — with a small gap that closes while you hover the row. Colors are a restyled take on Code OSS's Source Control Graph palette, kept legible on both themes: new lines rotate through gold, crimson, copper, emerald, and violet; the checked-out branch is blue, its upstream purple, and its base branch orange when that reference differs from the upstream (the configured Code OSS merge base, otherwise the default remote branch). Each row shows the subject (bold for the checked-out commit) with the dimmed author, then Code OSS's colored reference badges: the first reference with its name, and the rest as icon badges for branches, remote branches, and tags grouped by color, with a count when they stand for several references. Every badge is a capsule with fully rounded ends rather than a rounded square. The short ID, subject, author, relative time, and every reference are in the row tooltip; activating the row expands its changed files inline. Up to 60 commits are shown at first; reaching the end of the graph pane appends the next 60 earlier commits below the loaded rows (the same page is available from the "Load earlier commits" control at the end of the list), and the rows already shown keep their place while lines that ended at the old bottom connect to their commits. When the last page arrives no further page is offered, a page that fails to load keeps the loaded rows and offers retry, and refresh starts over from the newest page. Its section header carries Fetch, Pull and Push and the overflow menu.
- **Expanded commits**: click a commit row in the graph (or focus it and press `Enter` / `Space`) to list the files it changed directly below the row, as Code OSS's Source Control Graph does. Each file takes one 22-pixel row with the Web application's own file-type icon for its path (the glyph and color its file explorer uses, with the plugin's plain document icon as the fallback when the application provides none), its name, its dimmed directory and its colored status letter at the end, in path order; a renamed file's tooltip names its original path. The graph keeps running through the expanded rows: every line leaving the commit continues straight down, the commit's own line is drawn three pixels wide from its node down through the listed rows, and the commits below keep their shapes and colors. Several commits can stay expanded, and activating an expanded row collapses it. Click a file (or press `Enter`) to open its commit-scoped diff. While the list loads, when the commit changed nothing, when the read fails (with an inline retry) or when the list is capped, a single note row says so. Expanding never changes the repository, the change list or the commit box.
- **Commit details**: choose **View Details** at the top of a commit row's context menu to open that commit's details as a bordered, frosted card above the panel, using the same theme-derived translucency and backdrop blur as the bottom operation prompt and a solid fallback where filtering is unavailable. The change list, graph and commit box stay in place beneath it; while the card is open they accept no pointer or keyboard input and are hidden from assistive technology, and the card shows short ID, subject, author, relative time, message body, and the files the commit changed as a folder tree. Each folder appears once as a row above its contents, one indentation level per depth; a folder whose subtree is a single unbranched chain of folders collapses into one row that joins the names with `/` (for example `aa/bb/cc`), so the chain costs one indentation level instead of one per folder, and a file inside a folder or more than one child ends the collapse there. Within a folder, subfolders come before files, both ordered by name case-insensitively with numeric runs compared as numbers. Each folder row shows an expansion arrow in place of a folder glyph, pointing right while collapsed and down while expanded, and starts expanded for each commit; clicking it or pressing Enter or Space hides or shows its whole subtree, and a folder row opens no diff and no menu. Each file row keeps its own file-type icon, its rename source, and its status letter at the row's end in that status's color. Click a changed file to open its commit-scoped diff. The card slides in from the pane's right edge and back out that way, revealing the content beneath it. The back control returns to the change list and graph at the previous split ratio and scroll positions, with the same commits expanded, without touching the repository. Escape does the same while the card is open, unless an operation prompt or the branch menu is open and owns the key. A commit that changed nothing relative to its first parent says so, a failure is reported with retry, and at most 1,000 changed files are listed.
- **Diff tab**: click any changed file. Staged entries compare the index with the committed version, unstaged entries compare the working tree with the index, and untracked entries render as additions. A file opened from an expanded commit or a commit's details compares that commit with its first parent — the empty tree for a root commit — and the header names the commit; a pure rename is explained instead of showing an empty diff. Binary and oversized files are identified rather than decoded.

## Remote operations

The branch header keeps the branch chip and the refresh control. The commit graph's section header shows Fetch, Pull and Push as larger icon controls, styled after Code OSS's Source Control Graph, and the header highlights as a whole on hover, with the control under the pointer adding its own highlight on top. Fetch is labelled as fetching from every remote and uses a dashed twin-tail arrow, so it stays distinct from Pull. The header's overflow ellipsis opens Pull (Rebase), Sync, Publish Branch when the branch has no upstream, and a Remote group with Add Remote and Remove Remote. Fetch updates every configured remote's tracking branches and prunes those whose remote ref was deleted; it works even with a detached or unborn HEAD. Pull merges the upstream; Pull (Rebase) rebases the local commits onto it. Push sends the current branch to its upstream. Pull and Push are unavailable when the current branch has no upstream. Sync pulls by merging and then pushes, and stops before pushing when the pull fails. These actions are unavailable while another Git operation runs.

Publishing a branch without an upstream pushes it to a chosen remote and sets that remote branch as its upstream. With one remote it publishes immediately; with several it opens a form that prefers `origin`; with none it explains that a remote must be added. The branch picker also lists remote-tracking branches such as `origin/main` in their own group, excluding the symbolic remote `HEAD`. Picking one checks out a local branch with the same short name; when it does not exist the panel creates it with the remote branch as its upstream, and when it already exists the existing local branch is checked out without changing its upstream.

Add Remote asks for a name and URL and writes the repository configuration; Remove Remote lists the configured remotes and asks for confirmation before removing the chosen one. Remote names and URLs are validated, a failed or cancelled form changes nothing, and removing a remote also removes its remote-tracking branches. The remote list loads on demand, shows loading and failure states, and refreshes after a change.

Remote operations run on the Host without a shell, disable the terminal prompts Git controls, and are bounded by a timeout; a remote that needs credentials the Host cannot obtain ends with Git's message or a timeout. Configure a credential helper or an SSH agent for authentication; the plugin does not store credentials. Adding a remote writes repository configuration and authorizes later network operations to that URL, so Git's configured transports, credential helpers and hooks remain part of the local trust boundary.

Status refreshes when the panel opens, after every action, and when the refresh control is used. While the tab is visible the Host also watches the repository, so an edit, stage, commit, fetch, or branch switch made in a terminal appears on its own within about two seconds: a working-tree or index change refreshes the summary and change list, while a `HEAD` or reference change also moves the graph's checked-out, upstream, and base colors and badges on the rows already loaded, without returning the graph to its first page. The newest page is reloaded only when the checked-out commit is not among the loaded rows. If the Host cannot watch the files, the panel falls back to checking the status every few seconds, and no watcher failure is shown.

## Operation feedback

Every operation notice uses DSH's native Toast — the shell's own success check for succeeded operations and its warning icon for failures — instead of inserting a notice block into the panel. Successful commits (including amend, stage-all-and-commit, and the remote step of commit-and-push or commit-and-sync), ignores, detached checkout, branch creation/deletion, tag creation, remote synchronization, publishing, remote configuration and remote-branch checkout use success feedback; stale-target and busy menu messages do not. Toast placement, replacement and dismissal follow the host application and do not resize the change list or graph. Messages follow the selected language, and ignoring a tracked file still explains that it remains tracked.

Git failures are reported as a non-success Toast with the warning icon and, when the read can be retried, a localized retry action; a failed operation never emits a success Toast. Open operation forms stay open with their entered values while the failure shows, and the graph, commit-details and diff panes keep a compact retry state after the notice fades. If the native Toast and the shared service are both unavailable, inline Git controls, message clearing and refreshes continue to work without a private notification fallback.

## Operation panels

Discard confirmations, the offer to stage all changes before committing, and branch/tag forms float above the bottom of the Git panel without shrinking the change list or graph or moving their divider. They rise from the pane's bottom edge when they open and lower out of view again when dismissed, and the pane's content and scroll position stay put while they move. They expand with the pane width, overlaying the content beneath them with equal 4px gaps at the left, right and bottom. They share a rounded, translucent frosted surface that follows the native theme, with a solid background fallback when backdrop filtering is unavailable.

Copy and fields appear above a separate action footer. Long filenames, branch names and button labels wrap in narrow panes; taller forms scroll internally while their actions remain reachable. Reference-operation failures appear inside the open form and keep the entered values. Uncovered areas of the panel stay usable; requesting another prompt replaces the idle prompt rather than stacking cards or executing the replaced operation.

Plain confirmations start on **Cancel**, and idle `Escape` cancels without running Git. A prompt on its way out accepts no input. When the system asks for reduced motion, both surfaces appear and leave in place without moving. Reference creation starts in the name input. Pending operations prevent cancellation and duplicate submission.

## Context menus

Right-click a row, or focus a changed file or commit (or a button inside a group or diff header) and press the context-menu key or `Shift+F10`. Menus use the application's shared context-menu presentation, so position, dismissal, focus return, theme, and language match the rest of DSH.

- **Changed file**: open changes, stage or unstage, discard when the file can be discarded, **Add to .gitignore**, and copy its relative or full path. Ignoring appends a root-anchored literal path rule to the `.gitignore` at the repository root, preserves its existing content and line-ending style, and does not duplicate an identical rule. An untracked file stays on disk but leaves the refreshed change list; a tracked file stays tracked and the success Toast says so. A symbolic link or another non-regular `.gitignore` target is rejected without changing its target. A failed write is reported and never shown as a successful ignore.
- **Group header**: the group-level actions that apply to that group: stage or unstage every file in it, discard every change in it, and refresh.
- **Commit**: **View Details** first (available even while another operation runs, since it only reads), a separator, then Code OSS's action groups, in this order: a **Checkout** submenu of the local branch heads on that commit when present (the current branch is disabled), **Checkout (Detached)**, a separator, **Create branch**, a **Delete branch** submenu of the non-current local heads when present, a separator, **Create tag**, another separator, **Copy Commit Hash**, and **Copy Commit Message**. Remote branches, tags and HEAD markers are not branch submenu entries. The copy commands retain their original payloads: the full commit identifier and the subject line only, without adding the message body.
- **Diff header**: copy the file's relative or full path.
- **Expanded-commit or commit-details file**: copy its relative or full path. A past commit is history, so staging, unstaging, and discarding are not offered there.

Creating a branch asks for its name, points it at the chosen commit and checks it out. Creating a tag asks for a name and an optional message: no message makes a lightweight tag, while a non-empty message makes an annotated tag. Empty names and cancellations run no Git command, and a failed creation leaves the entered text available for correction. Deleting a branch asks for confirmation and Git refuses to delete the current or an unmerged branch. Name entries receive initial focus; deletion starts on Cancel, and idle Escape cancels. Closing restores the originating commit row's focus while it is still present. Ordinary Enter inserts a newline in a tag annotation; use the button or Ctrl/Cmd+Enter to submit. Pending operations expose their progress and retain text and logical focus on failure. Successful reference operations refresh the branch header, changes and graph.

Full paths are formed from the repository root, which may differ from the Session's working directory when the Session runs in a subdirectory of the repository. The subject is the first line of a commit message, not its body.

Menu commands behave like the equivalent hover control: same confirmation, same failure report, and same refresh. While a Git operation is running, commands that change the repository are disabled, and a command whose change disappeared in the meantime reports that instead of doing nothing. Opening a menu runs no Git command. Copies confirm success, and an unavailable clipboard is reported instead of being ignored. Without a context-menu facility in the host application, the panel and all of its inline controls keep working.

## Host execution and trust

Every Git command runs on the Host in the Session's working directory, through a single local route (`/api/dsh-git-graph/rpc`). The route accepts only unproxied loopback requests with the bundle's own request header and same-origin browser markers; it never runs through a shell and never accepts a repository path from the browser.

File paths are literal names, not Git wildcard or pathspec expressions, so selecting a name containing pattern characters does not select other matching files. Untracked previews and deletion verify the current Git classification rather than trusting an old row's flag. Direct file access refuses symbolic-link parent directories, and an untracked preview also refuses a symbolic link or a non-regular file. Discarding an untracked symbolic link itself removes only that link, not its target.

Remote operations use the same route and argument-vector execution. The browser sends only the operation, a remote name, a branch name, or a remote URL; the Host resolves the repository from the Session and validates those fields before Git sees them. Fetch, Pull, Push, Sync and Publish run with the terminal prompts Git controls disabled and a bounded duration, so a remote that needs input the Host cannot provide ends with Git's message or a timeout. Adding a remote writes repository configuration and authorizes later network operations to that URL.

The repository and local account remain trusted: normal Git hooks and configured helpers can still run. These path checks are not an operating-system sandbox against a local process concurrently replacing ancestor directories.

## Limitations

- Authentication must be non-interactive: configure a credential helper or an SSH agent. Credentials are not stored, a remote that needs input the Host cannot provide ends with an error or a timeout, and an in-flight remote operation cannot be cancelled from the panel.
- No force push, push to an arbitrary remote when an upstream already exists, remote tag push, remote branch deletion, remote rename, or editing a remote's fetch and push URLs after creation.
- No stash, arbitrary merge or rebase, or repository initialization. Amend only replaces the tip commit, from the commit action menu. Pull can merge or rebase, and tag creation is local and lightweight or annotated; there are no remote-tag operations.
- Conflicts can be staged to mark them resolved, but there is no merge editor.
- One repository at a time; the one containing the Session's working directory.
- A commit's changed files and per-file diff compare against its first parent; comparing against a second parent, another arbitrary commit, or the working tree is not offered.
- The panel is UI only. No agent tool exposes these operations, so the model cannot stage or commit on its own.
