# Git source control

A VS Code-style source-control surface for the right Sidebar. It reads the Git repository that contains the current Session's working directory and lets you review and act on it without leaving the Web GUI.

The panel is drawn with the host's own theme tokens, type scale, and component conventions, so it follows light and dark themes and matches the Sidebar's rows, headers, dividers, controls, and menus.

## Open it

Open the right Sidebar (the expand control at the conversation header's right corner), then pick **Source control** on the guide page. The same page opens with the sidebar toggle shortcut: `Ctrl+Shift+G` on Windows and Linux, `Cmd+Shift+G` on macOS.

The Git tab and its diff tabs live in the right Sidebar's normal docking surface, so they can be split, floating, or restored with the Sidebar's saved layout.

## What it shows

- **Branch header**: the checked-out branch, detached or unborn state, upstream tracking, and ahead/behind counts. Pick the header to switch to another local branch.
- **Commit box**: a multi-line message with `Ctrl+Enter` (`Cmd+Enter` on macOS) to commit. The box is one line high until the message wraps, grows with it, and stops at ten lines, where the message scrolls instead of pushing the change list down. Staged changes only; when nothing is staged, committing offers to stage every change first. A failed commit keeps the message and the staged files.
- **Merge changes / Staged changes / Changes**: VS Code's three change groups, each a single-layer, path-sorted list with no folder rows. Every row carries a status letter (`M` modified, `A` added, `D` deleted, `R` renamed, `U` untracked, `!` conflicted), the file's own file-type icon (the glyph and color the Web application's explorer uses, with the plugin's plain document icon as the fallback), the file name, and its dimmed parent directory; the full path is in the row tooltip. Hover a row for its stage, unstage, or discard action. When the working tree is clean, the change area says so in text, without an icon.
- **Resizable panes**: the change groups scroll in their own pane above the commit graph, so a long change list does not bury history. Drag the divider between them to change the split; with the divider focused, `ArrowUp`/`ArrowDown` move it by 5%, `PageUp`/`PageDown` by 10%, and `Home`/`End` jump to the limits. Each pane keeps a usable minimum height and its own scroll position. The ratio survives opening a commit's details and returning, but resets when the tab is closed and reopened.
- **Pinned headers**: while a change group or the graph is taller than its pane, its section header stays at the pane's top edge as you scroll, painted on the panel surface so the rows pass beneath it and nothing shows above it. The header already sits in that position before the pane is scrolled, so beginning to scroll moves only the rows. The next section's header takes that place as the previous section leaves, so only one header is pinned at a time.
- **Graph**: a reproduction of VS Code's Source Control Graph for recent commits across local branches, tags, and remote-tracking branches, listed in topological order as VS Code's "All" filter lists them. Lines follow VS Code's swimlane rules: a commit sits on the leftmost line heading for it and its first parent continues there; further lines heading for the same commit curve into its node on that row; each extra merge parent opens a new line at the right end; and lines to the right of an ended line shift left. Rows are 22 pixels high with an 11-pixel lane pitch, thin lines, quarter-turn joins and merges, and short S-turns for shifts; a lane stays unbroken where two rows meet, at any zoom. Nodes use VS Code's shapes — a dot, a ring around a dot for merges, and a hollow ring for the checked-out commit — with a small gap that closes while you hover the row. Colors follow VS Code: new lines rotate through amber, magenta, brown, teal, and violet; the checked-out branch is blue, its upstream purple, and its base branch orange (the configured VS Code merge base, otherwise the default remote branch). Each row shows the subject (bold for the checked-out commit) with the dimmed author, then VS Code's colored reference badges: the first reference with its name, and the rest as icon badges for branches, remote branches, and tags grouped by color, with a count when they stand for several references. The short ID, relative time, and every reference are in the row tooltip; activating the row expands its changed files inline. Up to 60 commits are shown at first; reaching the end of the graph pane appends the next 60 earlier commits below the loaded rows (the same page is available from the "Load earlier commits" control at the end of the list), and the rows already shown keep their place while lines that ended at the old bottom connect to their commits. When the last page arrives no further page is offered, a page that fails to load keeps the loaded rows and offers retry, and refresh starts over from the newest page.
- **Expanded commits**: click a commit row in the graph (or focus it and press `Enter` / `Space`) to list the files it changed directly below the row, as VS Code's Source Control Graph does. Each file takes one 22-pixel row with the Web application's own file-type icon for its path (the glyph and color its file explorer uses, with the plugin's plain document icon as the fallback when the application provides none), its name, its dimmed directory and its colored status letter at the end, in path order; a renamed file's tooltip names its original path. The graph keeps running through the expanded rows: every line leaving the commit continues straight down, the commit's own line is drawn three pixels wide from its node down through the listed rows, and the commits below keep their shapes and colors. Several commits can stay expanded, and activating an expanded row collapses it. Click a file (or press `Enter`) to open its commit-scoped diff. While the list loads, when the commit changed nothing, when the read fails (with an inline retry) or when the list is capped, a single note row says so. Expanding never changes the repository, the change list or the commit box.
- **Commit details**: choose **View Details** at the top of a commit row's context menu to open that commit's details as a bordered, frosted card above the panel, using the same theme-derived translucency and backdrop blur as the bottom operation prompt and a solid fallback where filtering is unavailable. The change list, graph and commit box stay in place beneath it, and the card shows short ID, subject, author, relative time, message body, and a single-layer, path-sorted list of the files the commit changed, each with its own file-type icon, its status letter and its rename source. Click a changed file to open its commit-scoped diff. The card slides in from the pane's right edge and back out that way, revealing the content beneath it. The back control returns to the change list and graph at the previous split ratio and scroll positions, with the same commits expanded, without touching the repository. Escape does the same while the card is open, unless an operation prompt or the branch menu is open and owns the key. A commit that changed nothing relative to its first parent says so, a failure is reported with retry, and at most 1,000 changed files are listed.
- **Diff tab**: click any changed file. Staged entries compare the index with the committed version, unstaged entries compare the working tree with the index, and untracked entries render as additions. A file opened from an expanded commit or a commit's details compares that commit with its first parent — the empty tree for a root commit — and the header names the commit; a pure rename is explained instead of showing an empty diff. Binary and oversized files are identified rather than decoded.

Status refreshes when the panel opens, after every action, and when the refresh control is used. While the tab is visible the Host also watches the repository, so an edit, stage, commit, fetch, or branch switch made in a terminal appears on its own within about two seconds: a working-tree or index change refreshes the summary and change list, while a `HEAD` or reference change also moves the graph's checked-out, upstream, and base colors and badges on the rows already loaded, without returning the graph to its first page. The newest page is reloaded only when the checked-out commit is not among the loaded rows. If the Host cannot watch the files, the panel falls back to checking the status every few seconds, and no watcher failure is shown.

## Operation feedback

Existing operation notices use DSH's shared Toast, just like clipboard feedback, instead of inserting a green notice into the panel. Successful commits (including stage-all-and-commit), ignores, detached checkout, branch creation/deletion and tag creation use success feedback; stale-target and busy menu messages do not. Toast placement, replacement and dismissal follow the host application and do not resize the change list or graph. Messages follow the selected language, and ignoring a tracked file still explains that it remains tracked.

Git failures stay in their existing inline banner or open operation form; a failed operation never emits a success Toast. If host notifications are unavailable, inline Git controls, message clearing and refreshes continue to work without a private notification fallback.

## Operation panels

Discard confirmations, the offer to stage all changes before committing, and branch/tag forms float above the bottom of the Git panel without shrinking the change list or graph or moving their divider. They rise from the pane's bottom edge when they open and lower out of view again when dismissed, and the pane's content and scroll position stay put while they move. They expand with the pane width, overlaying the content beneath them with equal 4px gaps at the left, right and bottom. They share a rounded, translucent frosted surface that follows the native theme, with a solid background fallback when backdrop filtering is unavailable.

Copy and fields appear above a separate action footer. Long filenames, branch names and button labels wrap in narrow panes; taller forms scroll internally while their actions remain reachable. Reference-operation failures appear inside the open form and keep the entered values. Uncovered areas of the panel stay usable; requesting another prompt replaces the idle prompt rather than stacking cards or executing the replaced operation.

Plain confirmations start on **Cancel**, and idle `Escape` cancels without running Git. A prompt on its way out accepts no input. When the system asks for reduced motion, both surfaces appear and leave in place without moving. Reference creation starts in the name input. Pending operations prevent cancellation and duplicate submission.

## Context menus

Right-click a row, or focus a changed file or commit (or a button inside a group or diff header) and press the context-menu key or `Shift+F10`. Menus use the application's shared context-menu presentation, so position, dismissal, focus return, theme, and language match the rest of DSH.

- **Changed file**: open changes, stage or unstage, discard when the file can be discarded, **Add to .gitignore**, and copy its relative or full path. Ignoring appends a root-anchored literal path rule to the `.gitignore` at the repository root, preserves its existing content and line-ending style, and does not duplicate an identical rule. An untracked file stays on disk but leaves the refreshed change list; a tracked file stays tracked and the success Toast says so. A symbolic link or another non-regular `.gitignore` target is rejected without changing its target. A failed write is reported and never shown as a successful ignore.
- **Group header**: the group-level actions that apply to that group: stage or unstage every file in it, discard every change in it, and refresh.
- **Commit**: **View Details** first (available even while another operation runs, since it only reads), a separator, then VS Code's action groups, in this order: a **Checkout** submenu of the local branch heads on that commit when present (the current branch is disabled), **Checkout (Detached)**, a separator, **Create branch**, a **Delete branch** submenu of the non-current local heads when present, a separator, **Create tag**, another separator, **Copy Commit Hash**, and **Copy Commit Message**. Remote branches, tags and HEAD markers are not branch submenu entries. The copy commands retain their original payloads: the full commit identifier and the subject line only, without adding the message body.
- **Diff header**: copy the file's relative or full path.
- **Expanded-commit or commit-details file**: copy its relative or full path. A past commit is history, so staging, unstaging, and discarding are not offered there.

Creating a branch asks for its name, points it at the chosen commit and checks it out. Creating a tag asks for a name and an optional message: no message makes a lightweight tag, while a non-empty message makes an annotated tag. Empty names and cancellations run no Git command, and a failed creation leaves the entered text available for correction. Deleting a branch asks for confirmation and Git refuses to delete the current or an unmerged branch. Name entries receive initial focus; deletion starts on Cancel, and idle Escape cancels. Closing restores the originating commit row's focus while it is still present. Ordinary Enter inserts a newline in a tag annotation; use the button or Ctrl/Cmd+Enter to submit. Pending operations expose their progress and retain text and logical focus on failure. Successful reference operations refresh the branch header, changes and graph.

Full paths are formed from the repository root, which may differ from the Session's working directory when the Session runs in a subdirectory of the repository. The subject is the first line of a commit message, not its body.

Menu commands behave like the equivalent hover control: same confirmation, same failure report, and same refresh. While a Git operation is running, commands that change the repository are disabled, and a command whose change disappeared in the meantime reports that instead of doing nothing. Opening a menu runs no Git command. Copies confirm success, and an unavailable clipboard is reported instead of being ignored. Without a context-menu facility in the host application, the panel and all of its inline controls keep working.

## Host execution and trust

Every Git command runs on the Host in the Session's working directory, through a single local route (`/api/dsh-git-graph/rpc`). The route accepts only unproxied loopback requests with the bundle's own request header and same-origin browser markers; it never runs through a shell and never accepts a repository path from the browser.

File paths are literal names, not Git wildcard or pathspec expressions, so selecting a name containing pattern characters does not select other matching files. Untracked previews and deletion verify the current Git classification rather than trusting an old row's flag. Direct file access refuses symbolic-link parent directories, and an untracked preview also refuses a symbolic link or a non-regular file. Discarding an untracked symbolic link itself removes only that link, not its target.

The repository and local account remain trusted: normal Git hooks and configured helpers can still run. These path checks are not an operating-system sandbox against a local process concurrently replacing ancestor directories.

## Limitations

- No network operations: fetch, pull, push, and remote management are not part of this bundle.
- No stash, merge, rebase, amend, or repository initialization. Tag creation is local and lightweight or annotated; there are no remote-tag operations.
- Conflicts can be staged to mark them resolved, but there is no merge editor.
- One repository at a time; the one containing the Session's working directory.
- A commit's changed files and per-file diff compare against its first parent; comparing against a second parent, another arbitrary commit, or the working tree is not offered.
- The panel is UI only. No agent tool exposes these operations, so the model cannot stage or commit on its own.
